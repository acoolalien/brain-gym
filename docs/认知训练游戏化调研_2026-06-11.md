# 认知训练小游戏：技术调研与 Hana 卡片插件可行性分析

> 调研时间：2026-06-11 | 来源：学术文献 + 产品分析 + 开源代码 + Hana SDK 文档

---

## 一、认知训练的分类体系与科学原理

### 1.1 主要认知域

| 认知域 | 核心神经机制 | 代表性训练范式 | 迁移效应证据 |
|--------|------------|--------------|------------|
| **工作记忆** | 前额叶-顶叶网络，多巴胺调控 | N-Back、数字广度、Corsi 积木 | 近迁移稳健，远迁移争议（Jaeggi 2008 结果未完全复现） |
| **注意力** | 前额叶-顶叶注意网络（背侧/腹侧） | Flanker、持续注意反应任务(SART)、舒尔特表格 | 中等，选择性注意训练对日常任务有迁移 |
| **执行功能/抑制控制** | 前额叶皮层（DLPFC、ACC） | Stroop、Go/No-Go、停止信号任务 | 近迁移稳定，日常冲动控制有适度迁移 |
| **认知灵活性** | 前额叶-基底节环路 | 任务切换、WCST（威斯康星卡片分类） | 中等，对多任务处理有帮助 |
| **处理速度** | 全脑白质完整性和髓鞘化 | 符号数字替换、视觉搜索 | BrainHQ Double Decision 有 RCT 证据（ACTIVE 研究，10年随访） |
| **情景记忆** | 海马体-内侧颞叶 | 序列记忆、面孔-名字关联、物体位置回忆 | 策略训练有改善，纯重复练习效果有限 |
| **空间能力** | 顶叶-海马旁回 | 心理旋转、Corsi 积木（倒序） | 领域特异性强，迁移有限 |
| **流体智力（Gf）** | 广泛的前额叶-顶叶网络 | 双重 N-Back、关系推理 | 争议最大，早期 Jaeggi (2008) 效应后续研究未充分复现 |

### 1.2 最稳健的分类框架

- **DSM-5 六大认知域**：复杂注意、执行功能、学习和记忆、语言、知觉运动、社会认知
- **Miyake 三因子执行功能模型**（2000）：抑制（Inhibition）、更新（Updating）、切换（Shifting）——这是目前认知训练研究中被引用最多的模型

不同域的训练效果差异极大。处理速度和空间能力是唯二在大型 RCT 中展现远期迁移证据的域。

### 1.3 关键科学原则

1. **特异性原则**：大脑优化训练的具体任务，而非"认知能力"本身。这解释了为什么 Sudoku 大师只在 Sudoku 上强。
2. **剂量效应**：npj Digital Medicine（2024，n=8,709）表明 60 岁以下最优剂量为 **25-30 分钟/天**。20 分钟 4-5 天/周 × 4-8 周是多数研究中的有效方案。
3. **适应性难度**：训练须保持在「近端发展区」（70-85% 正确率），太难导致挫败，太易无刺激。
4. **多域组合 > 单域**：同时训练多个认知域比单一任务更可能产生迁移（Klingberg, 2010）。
5. **加工速度优先**：ACTIVE 研究（n=2,802，10年随访）证明处理速度训练是证据最强的单一干预，训练组痴呆风险降低 29%。

### 1.4 碎片化训练的证据

每天 3-5 分钟训练的**独立有效性证据为零**。夏一的调研指出三个硬伤：
1. **神经可塑性需要持续活动窗口**——突触强化需要 >15 分钟的持续刺激
2. **暖身时间吃掉训练时间**——前 1-2 分钟是任务熟悉阶段，并非有效训练
3. **缺乏渐进超负荷空间**——3 分钟内无法完成"热身→挑战→超负荷"的完整训练循环

唯一的可行辩护路径：通过高频（每天必做）× 长期坚持（365 天）累积总剂量，而非依赖单次训练强度。定位为「认知热身」或「习惯锚点」比「训练」更诚实。

### 1.5 舒尔特表格的学术地位

需要注意：舒尔特表格虽然广泛用于飞行员/运动员选拔，但在经同行评议的认知训练文献中几乎不存在。它更接近**注意力的现场测试工具**而非经过验证的**训练干预手段**。这降低了它的科学推荐优先级，但不影响它作为低门槛互动游戏的价值——只要不宣称它有认知增强效果。

## 二、适合做成小游戏的认知训练科目

按「卡片化可行性」排序，评估维度：
- **机制简洁度**：能否用 1-2 种交互完成（点击/选择/拖拽）
- **反馈即时性**：是否能在单次交互后立刻给出对/错反馈
- **碎片化适应性**：是否适合 1-3 分钟的短会话
- **游戏化潜力**：是否能自然嵌入进度/分数/成就系统
- **卡片空间适配**：是否能在小尺寸 iframe（约 350×400px）内完整呈现

### 2.1 强推荐（机制简洁、卡片适配极好）

#### 🅰 **舒尔特表格** ⭐⭐⭐⭐
- **训练目标**：视觉搜索速度、注意力集中度
- **机制**：5×5 网格，数字 1-25 随机排列，按升序点击
- **卡片适配**：完美。网格天然适合卡片布局，只需要点击交互
- **游戏化方向**：计时排行榜、每日挑战（不同排列）、难度升级（6×6→7×7）、连击特效
- **实现复杂度**：低。纯 JS 可在 200 行内完成
- **科学依据**：广泛应用但学术文献薄弱——在经同行评议的认知训练文献中几乎不存在。更接近注意力测试工具而非训练干预手段。游戏性价值 > 科学训练价值。

#### 🅱 **Stroop 色词任务** ⭐⭐⭐⭐⭐
- **训练目标**：抑制控制、选择性注意
- **机制**：屏幕显示颜色词（如红色字体的"蓝"），玩家选择/说出字体的颜色而非词义
- **卡片适配**：极好。单字+颜色按钮，卡片空间绰绰有余
- **游戏化方向**：连击数、干扰升级（更多颜色、更快的切换）、反向模式（选择词义忽略颜色）
- **实现复杂度**：极低。核心逻辑 < 100 行
- **科学依据**：1935 年 Stroop 原始实验，认知心理学最经典范式之一

#### 🅲 **Go/No-Go 反应抑制** ⭐⭐⭐⭐
- **训练目标**：反应抑制、冲动控制
- **机制**：连续出现刺激，对目标刺激按键（Go），对非目标刺激不反应（No-Go）
- **卡片适配**：好。一个刺激显示区 + 一个按钮。需要精确的计时
- **游戏化方向**：速度-准确率权衡、稀有目标高奖励、干扰项多样性
- **实现复杂度**：低。核心是计时精度
- **科学依据**：广泛应用于 ADHD 评估和训练

#### 🅳 **数字广度/序列记忆** ⭐⭐⭐⭐
- **训练目标**：工作记忆广度、听觉/视觉序列记忆
- **机制**：依次展示数字/符号序列，用户按相同顺序（正序）或相反顺序（倒序）复述
- **卡片适配**：好。纯视觉/触控序列，适合卡片空间
- **游戏化方向**：逐步增加长度、不同类别（数字→字母→颜色→混合）、记忆宫殿主题
- **实现复杂度**：低。状态机管理序列即可
- **科学依据**：WAIS 智力测验的核心分测验之一

### 2.2 中等推荐（机制略复杂，需权衡卡片空间）

#### 🅴 **N-Back（单模态视觉版）** ⭐⭐⭐
- **训练目标**：工作记忆更新、流体智力
- **机制**：位置/图形依次出现，判断当前刺激是否与 N 步前相同
- **卡片适配**：中等。需要 3×3 位置网格 + 两个按钮（匹配/不匹配）。紧凑可行
- **游戏化方向**：N 级别自适应（1-back→2-back→3-back）、双模态挑战（位置+颜色）
- **实现复杂度**：中。需要队列管理 N 步历史，自适应难度算法
- **科学依据**：最受研究的认知训练范式。近迁移稳健，但对流体智力的远迁移声称已被多篇元分析削弱（Au et al., 2015 等）。定位为「工作记忆练习」而非「智力提升」。

#### 🅵 **任务切换** ⭐⭐⭐
- **训练目标**：认知灵活性、任务集切换成本
- **机制**：任务规则随机切换（如"数字→判断奇偶；字母→判断元音"），用颜色/位置提示当前规则
- **卡片适配**：一般。需要明确的任务提示区+快速响应，卡片可以但交互密度高
- **游戏化方向**：多任务混搭、切换成本可视化、随机规则生成
- **实现复杂度**：中高。多规则集管理、切换成本计算
- **科学依据**：任务切换范式是执行功能研究的标准工具

#### 🅶 **心理旋转** ⭐⭐⭐⭐
- **训练目标**：空间工作记忆、视觉空间能力
- **机制**：展示两个 3D 几何体（一个旋转了一定角度），判断两者是否相同
- **卡片适配**：一般。需要较大的图形展示区
- **游戏化方向**：角度难度递增、计时赛、复杂形状解锁
- **实现复杂度**：中高。需要预置 3D 图形资源或 SVG 旋转计算
- **科学依据**：Shepard & Metzler (1971) 经典实验。远迁移证据较强（→ STEM 能力，★★★★），是少数有远迁移证据的训练科目之一。实现成本高但科学回报也高。

### 2.3 不推荐（卡片适配差或实现过于复杂）

#### ❌ **双重 N-Back** ⭐⭐
- 理由：视觉+听觉双通道，卡片空间的听觉输出不可靠，交互复杂度超过卡片能承载的

#### ❌ **WCST（威斯康星卡片分类）** ⭐
- 理由：需要大量卡片排列和规则推断，单次会话时间太长（通常 10-15 分钟）

#### ❌ **Flanker 箭头任务** ⭐
- 理由：需要极高精度的反应时测量（毫秒级），浏览器 iframe 的计时精度不够

## 三、游戏化改造的关键设计原则

### 3.1 JMIR 框架要点（Khaleghi et al., 2021）

1. **游戏元素不能引入无关认知负荷**——闪屏特效、复杂 UI 动画会污染认知测量
2. **两种改造路径**：
   - 给现有认知任务加游戏元素（加分、进度条、成就徽章）→ 适合我们
   - 将现有游戏映射到认知功能 → 需要更大设计投入
3. **OMDE 设计线**：对象→机制→动态→情感，四层逐步细化

### 3.2 实操设计约束

| 原则 | 正确做法 | 错误做法 |
|------|---------|---------|
| 难度自适应 | 根据连续 3 次正确/错误自动调级 | 固定难度导致挫败或无聊 |
| 反馈即时但不喧宾夺主 | 单次响应后 200ms 内显示√/✗，然后进入下一试次 | 过关动画占 2 秒，打断训练节奏 |
| 分数可见但不制造焦虑 | "今日最高连击：12" | "你击败了 95% 的用户！"（制造社会比较压力） |
| 主题轻量化 | 简洁的视觉主题（颜色区分、形状编码） | 复杂的叙事背景、角色系统 |
| 会话粒度 | 单次 25-40 个试次，1-3 分钟完成 | 需要 5+ 分钟才能完成一轮 |

## 四、Hana 卡片插件可行性评估

### 4.1 基础事实

Hana 的 card/widget/page 本质上**全部是 iframe**。不存在独立的「card 组件类型」——你在 UI 中看到的信息卡、仪表盘、知识图谱，都是一个由插件 route 服务端渲染的 HTML iframe。这个 iframe 通过 `window.postMessage` 与宿主通信，内部可以运行任意 HTML/CSS/JS。

### 4.2 技术基座（以现有插件验证）

基于对 `@hana/plugin-sdk`、`@hana/plugin-components` 文档和现有插件（TODO/token-tracker/lightrag/TTS）源码的分析：

| 能力 | 状态 | 证据 |
|------|------|------|
| **纯 HTML/CSS/JS iframe** | ✅ 确认 | TODO widget 即纯 HTML iframe |
| **Canvas 2D 渲染** | ✅ 确认 | LightRAG 图谱用 Cytoscape.js；Token 仪表盘用 Chart.js |
| **Canvas/WebGL** | ✅ 可行 | iframe 方案完全允许 Three.js 等，限制仅在 widget 小面板性能 |
| **Audio 播放** | ✅ 确认 | TTS 播放器用 `<audio>` 标签 |
| **DOM 拖拽** | ✅ 确认 | TODO 拖拽排序（HTML5 Drag & Drop API） |
| **localStorage 持久化** | ✅ 确认 | TODO 用 localStorage 记住折叠状态，跨会话持久 |
| **sessionStorage** | ✅ 确认 | TTS 用 sessionStorage 防止重复播放 |
| **服务端数据持久化** | ✅ 确认 | TODO 将待办写入 `todos.json`，插件数据目录可读写 |
| **`performance.now()` 毫秒计时** | ✅ 确认 | 浏览器标准 API，iframe 内完全可用 |
| **iframe 尺寸自适应** | ✅ 确认 | `hana.ui.resize()` API |
| **React 组件库** | ✅ 确认 | `@hana/plugin-components` 提供 CardShell/Button/List 等 |
| **Hana 主题继承** | ✅ 确认 | `HanaThemeProvider mode="inherit"` |
| **Toast 通知** | ✅ 确认 | `hana.toast.show()` |
| **服务端推送（WebSocket/SSE）** | ❌ 不存在 | GitHub Issue #1056 明确提出需求 |
| **用户身份 API** | ❌ 不存在 | SDK 不暴露 `ctx.user`/`userId` → 可用 localStorage UUID 变通 |
| **Agent 主动推送内容到 iframe** | ❌ 不支持 | 只能 Agent → tool 写文件 → iframe 轮询感知 |

### 4.3 实时刷新方案

由于没有 WebSocket/SSE，只能轮询。已有模式（TODO 插件）：

```javascript
// 每 3-5 秒拉取最新数据
setTimeout(function poll() {
    fetch('/api/plugins/my-plugin/status').then(r => r.json()).then(render);
    setTimeout(poll, 3000);
}, 3000);
```

Agent 出题流程：Agent → 调 tool 写入题目 → 插件数据目录 → iframe 轮询 REST API → 感知新题目。这绕开了「Agent 不能推送到 iframe」的限制。

### 4.4 技术判断：所有候选游戏均可实现

| 游戏 | 技术基础 | 瓶颈 |
|------|---------|------|
| 舒尔特表格 | Canvas/DOM 渲染 + 点击事件 + `performance.now()` 计时 | 无 |
| Stroop 色词 | CSS 颜色 + 按钮选择 + 反应计时 | 无 |
| Go/No-Go | DOM 刺激序列 + 按键监听 + 计时 | 无 |
| 数字广度 | DOM 序列展示 + 输入框 + 状态机 | 无 |
| N-Back（单模态） | 网格渲染 + 队列管理 + 自适应难度 | 无 |
| 任务切换 | 多规则集管理 + 颜色提示 + 快速响应 | 无 |
| 心理旋转 | Canvas/SVG 渲染 3D 图形 + 旋转计算 | 较大的图形预置工作 |

**做不了的**：实时多人对战（无 WebSocket）、Agent 实时打断出题（无推送）、跨设备进度同步（无用户 API）。但这些不属于认知训练的核心需求。

### 4.5 架构方案

有两种模式可选：

**模式 A：纯 Widget（推荐 MVP）**
```
插件 iframe widget (侧边栏) ← 所有游戏逻辑在前端
                           ← localStorage 存分数/进度
                           ← 完全独立，不依赖 Agent
```
适合快速验证，零后端复杂度。TODO 插件即此模式。

**模式 B：Agent 联动（进阶）**
```
Agent (会话中) → tool 生成每日新题 → 插件数据目录
                                        ↓
iframe widget (侧边栏) ← poll (每3s) ← 插件 REST API ← 数据目录
                                        ↓
用户点击答题 → fetch POST → 插件 REST API → 写入答案文件
                                        ↓
Agent → tool 读取答案 → 评判 → 会话中输出反馈 + 成绩
```
适合需要 AI 生成题目、个性化评判的场景。TODO 插件就是这个模式——AI 通过 tool 添加待办，widget 轮询显示。

### 4.5 推荐的 MVP 路径

**第一阶段：验证卡片可行性（1-2 周）**
- 先做一个独立的 Widget（右侧面板），实现舒尔特表格 + Stroop
- 验证 iframe 内的计时精度、React 渲染性能、主题适配
- 不需要后端工具，纯前端游戏

**第二阶段：信息流集成（需确认能力后）**
- 如果 Hana 支持信息流卡片：做成每日一题推送
- 如果只支持 Widget：做成右侧面板的"脑力热身"入口
- 通过工具 `get-daily-challenge` 生成每日新题

**第三阶段：数据沉淀**
- 分数历史存储到 `ctx.dataDir`
- 进度可视化（简单的 SVG 折线图）
- 成就系统（连续打卡、最高分徽章）

### 4.6 关键风险

| 风险 | 严重度 | 缓解方案 |
|------|--------|---------|
| **信息流卡片能力不确定** | 高 | 先做 Widget 模式验证，等确认信息流能力后再切 |
| **iframe 计时精度不足** | 中 | Stroop/Go-NoGo 需要毫秒级 RT，用 `performance.now()` + requestAnimationFrame 可做到 5ms 精度，足够用 |
| **低频使用导致数据稀疏** | 中 | 设计极低的每日门槛（1 分钟），用 Toast 提醒机制保持参与 |
| **迁移效应有限** | 低 | 定位为「认知热身」而非「智商提升」，避免过度承诺 |
| **小剂量训练证据为零** | 高 | 定位为习惯养成而非训练干预，首屏标注"每次 1-3 分钟，认知拉伸练习" |
| **无用户隔离** | 中 | 如果多个用户在同一个 Hana 实例上使用，分数数据会混在一起。可通过 Agent/Session 归属做软隔离 |

## 五、结论与建议

### 5.1 回答三个核心问题

**Q1：认知训练有科学依据吗？**
有，但比营销宣传窄得多。最可靠的证据来自**处理速度训练**（BrainHQ Double Decision，ACTIVE 研究）和**工作记忆训练**（N-Back，近迁移稳健）。泛化的"变聪明"宣称已被 2014 年 70 位神经科学家联名公开信驳斥。正确的定位是「特定认知功能的靶向训练」。

**Q2：哪些科目适合做成小游戏？**
舒尔特表格、Stroop 色词、Go/No-Go、数字广度是最佳候选——机制简洁、单次交互周期短、卡片空间友好、有成熟开源实现可参考。N-Back 和任务切换作为进阶内容。

**Q3：能做进 Hana 卡片信息流吗？**
信息流卡片本质就是 iframe，技术路线已完全确认可行。已由程序猫通过 TODO/token-tracker/lightrag/TTS 四个现有插件交叉验证：Canvas/WebGL/Audio/localStorage/`performance.now()` 毫秒计时/iframe 尺寸自适应全部可用。两种实现模式：纯 Widget（前端自包含，MVP 推荐）或 Agent 联动（AI 出题 → widget 轮询 → 用户答题）。

### 5.2 核心设计定位

> **「脑力热身」而非「智商训练器」**

对标：Duolingo 的每日练习 = 低门槛、碎片化、习惯养成。不承诺认知增强，只提供「几分钟的大脑拉伸」。这个定位既符合现有科学证据，也符合 HanaAgent 的辅助工具生态位。
