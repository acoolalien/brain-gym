# Hana 卡片（PluginCard）能力边界源码级调研

> 调研日期：2026-06-11
> 参考实现：TTS 音频条（`tts-dev` 插件）
> 分析方法：从桌面端渲染管线逆向，以源码中常量/类型/sandbox/host 协议为唯一证据源

---

## 一、卡片渲染链路

### 1.1 从插件 tool 返回到桌面端 DOM 的完整管线

```
插件 tool.execute() → return { details: { card: { type, route, aspectRatio } } }
  ↓
服务端序列化为 chat message block（type: 'plugin_card'）
  ↓
block-renderers.ts → 分发到 PluginCardBlock
  ↓
PluginCardBlock.tsx → usePluginIframe({ slot: 'card' })
  ↓
<iframe sandbox="allow-scripts allow-same-origin" />
```

### 1.2 关键数据结构

```ts
// types.ts:276
export interface PluginCardDetails {
  type: string;         // "iframe" — 当前唯一支持的类型
  pluginId: string;
  route: string;        // 如 "/player?file=speech_xxx.mp3"
  title?: string;
  description: string;  // 不支持 iframe 时的降级文本
  aspectRatio?: string; // "8:1", "4:3", "1:1" 等
}
```

### 1.3 卡片 iframe 渲染配置

```tsx
// PluginCardBlock.tsx:62-73 — iframe 标签参数
<iframe
  sandbox="allow-scripts allow-same-origin"
  style={{ width: size.width ?? defaultW, height: size.height ?? defaultH }}
/>

// 约束常量（plugin-ui-host-controller.ts:46-49）
const CARD_MAX_WIDTH = 400;
const CARD_MAX_HEIGHT = 600;
const CARD_MIN_WIDTH = 50;
const CARD_MIN_HEIGHT = 30;

// usePluginIframe 调用（PluginCardBlock.tsx:40-48）
usePluginIframe(surfaceUrl.iframeSrc, {
  slot: 'card',
  initialSize: { width: defaultW, height: defaultH }, // 默认 400×300
  readyOnTimeout: true,   // ← 卡片特性：5s 后自动 ready，无需 hana.ready()
});
```

**源码证据**：`use-plugin-iframe.ts:59` — `readyOnTimeout` 为 true 时，握手超时后 `setStatus('ready')` 而非 `setStatus('error')`。

## 二、卡片 vs Widget 差异矩阵

### 2.1 Sandbox 权限

| 属性 | Card | Widget |
|------|------|--------|
| `allow-scripts` | ✅ | ✅ |
| `allow-same-origin` | ✅ | ✅ |
| `allow-forms` | ❌ | ✅ |
| `allow-popups` | ❌ | ✅ |

**源码**：`PluginCardBlock.tsx:66` vs `PluginWidgetView.tsx:59`

**影响**：
- 卡片内不能提交 `<form>`（但 fetch API 不受影响，所以表单数据可以用 JS fetch 发送）
- 卡片内不能 `window.open()` 弹出新窗口

### 2.2 尺寸约束

| 维度 | Card | Widget |
|------|------|--------|
| 最大宽度 | **400px** | 无硬限制（受面板宽度约束） |
| 最大高度 | **600px** | `viewportHeight - 48px` |
| 最小宽度 | 50px | 无硬限制 |
| 最小高度 | 30px | 100px |
| 宽高比控制 | `aspectRatio` 字段控制初始尺寸 | 无（自由 resize） |
| 用户手动调整大小 | 否（固定 iframe 尺寸） | 否（fill 面板） |

**源码**：`plugin-ui-host-controller.ts:211-231` — 卡片的 `clampPluginIframeSize` 分支使用 `CARD_MAX_WIDTH=400` 和 `CARD_MAX_HEIGHT=600` 做硬上限。

**关键发现**：卡片不支持用户手动拖拽调整大小。初始尺寸由 `aspectRatio` 计算，后续只能通过 `hana.resize()` 在 400×600 范围内动态调整。

### 2.3 UI 宿主能力（postMessage 协议）

| 能力 | Card | Widget | 需授权 |
|------|------|--------|--------|
| `hana.ready()` | ✅（可选，5s 超时自动 ready） | ✅（必须调用） | 否 |
| `hana.resize()` | ✅（受 400×600 限制） | ✅ | 否 |
| `hana.toast.show()` | ✅ | ✅ | 否 |
| `hana.external.open()` | ❌ | ✅ | 是 |
| `hana.clipboard.writeText()` | ❌ | ✅ | 是 |
| `hana.navigateTab()` | ❌ | ✅ | 否 |

**源码**：`capabilities.ts:81-103` — 各能力的 `allowedSlots` 数组。

`external.open` 和 `clipboard.writeText` 的 `allowedSlots` 中不含 `'card'`。**这是卡片和 Widget 之间最重要的能力差异**。

### 2.4 生命周期

| 维度 | Card | Widget |
|------|------|--------|
| 创建时机 | 插件 tool 返回 card details | 用户手动打开 Widget 面板 |
| 销毁时机 | 消息滚出视口时（Chrome iframe 优化） | Widget 面板关闭时 |
| 重新渲染 | 滚回视口时 iframe 重新加载（不可靠） | 面板重新打开时重新加载 |
| 状态保持 | 依赖 localStorage/sessionStorage | sessionStorage（同会话有效） |
| 与 Agent 消息的关联 | 嵌入在特定消息中 | 独立面板，与消息流分离 |

**TTS 参考**：TTS 音频条用 `sessionStorage` 记住播放状态。`player-template.js:27-29` 用 `STORAGE_KEY` 做防重复播放——这是一个已验证的卡内状态保持方案。

### 2.5 路由和资源访问

- **路由格式**：`/api/plugins/{pluginId}{route}` — 卡片和 Widget 共享同一套路由注册
- **资源访问**：`/api/plugins/{pluginId}/assets/` — 静态资源同样可用
- **数据目录**：通过插件 route handler 访问 `ctx.dataDir`，卡片 iframe 通过 fetch 调用插件自己的 REST API

**结论**：卡片在路由和资源访问上与 Widget 没有任何差异。所有插件 Node 端能力（数据目录读写、Agent API、sampleText）都可以通过卡片 iframe → fetch → 插件 route → Node 端处理这条链路间接使用。

## 三、认知训练游戏：逐项源码级验证

### 3.1 舒尔特表格（5×5 网格，点击交互）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| Canvas 渲染 | ✅ 可行 | sandbox 允许 `allow-scripts`，Canvas API 是 DOM 标准 API |
| 5×5 网格在 400×400 内 | ✅ 可行 | 每个格子 80×80px，在 400px 宽度内舒适 |
| 点击事件 | ✅ 可行 | 标准 DOM 事件，TTS 已使用 `click` 事件（player-template.js:41） |
| `performance.now()` 计时 | ✅ 可行 | 浏览器标准 API |
| 分数存储到 localStorage | ✅ 可行 | TTS 已验证 sessionStorage（player-template.js:22-23） |
| 卡片尺寸 | 推荐 `aspectRatio: "1:1"` | 正方形网格，400×400 刚好 |

**技术判断**：✅ 完全可行。舒尔特表格是卡片最适合的游戏类型。Canvas 渲染 5×5 网格 + 点击事件 + 毫秒计时，所有 API 均为浏览器标准，不受卡片 sandbox 限制。

### 3.2 Stroop 色词（颜色字 + 按钮选择）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| CSS 颜色控制 | ✅ 可行 | CSS 完全可用，TTS 已大量使用 inline CSS |
| 按钮点击 | ✅ 可行 | TTS 播放/暂停按钮已验证（player-template.js:41） |
| 反应计时 | ✅ 可行 | `performance.now()` |
| 连击/分数动画 | ✅ 可行 | CSS transition/animation 可用 |
| `allow-forms` 缺失 | 无影响 | fetch POST 代替 `<form>` 提交 |
| 卡片尺寸 | 推荐 `aspectRatio: "4:3"` | 400×300，留足文字和按钮空间 |

**技术判断**：✅ 完全可行。Stroop 的核心是文字颜色 + 按钮选择，不依赖任何受限 API。

### 3.3 Go/No-Go 反应抑制（刺激序列 + 按键/点击响应）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| 键盘事件（keydown） | ⚠️ 需要注意焦点 | iframe 必须获得焦点才能捕获键盘事件 |
| 点击事件替代 | ✅ 可行 | 用点击替代按键（如点击一个区域表示 Go） |
| 反应计时 | ✅ 可行 | `performance.now()` 精度 ~5ms |
| 刺激序列定时 | ✅ 可行 | `setTimeout`/`setInterval`/`requestAnimationFrame` |
| 卡片焦点管理 | ⚠️ 需要用户先点击卡片 | iframe 默认无焦点，首次按键需要先点击卡片区域 |

**技术判断**：✅ 可行，但推荐用点击交互替代键盘交互。卡片 iframe 需要用户先点击才能获得焦点——Go/No-Go 如果是按键版，用户需要额外操作。改为点击版（"看到目标点击大按钮，非目标不点"）可以完全规避焦点问题。

### 3.4 数字广度/序列记忆（序列展示 + 复述输入）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| 序列展示（DOM 定时切换） | ✅ 可行 | setTimeout/DOM 操作 |
| 输入框（`<input>`） | ✅ 可行 | HTML input 在 iframe 中完全可用 |
| `allow-forms` 缺失 | 无影响 | `<input>` 本身不需要 form 提交 |
| 按钮确认 | ✅ 可行 | 点击事件 |
| 卡片尺寸 | `aspectRatio: "4:3"` | 序列区 + 输入区 + 按钮 |

**技术判断**：✅ 完全可行。核心是 DOM 序列展示 + 输入框，无需受限 API。

### 3.5 N-Back 单模态（位置记忆 + 匹配判断）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| 3×3 网格渲染 | ✅ 可行 | Canvas 或 DOM 均可 |
| 位置闪烁动画 | ✅ 可行 | CSS animation / setTimeout |
| 匹配/不匹配按钮 | ✅ 可行 | 两个按钮 |
| N 步队列管理 | ✅ 可行 | JS 数组操作 |
| 自适应难度 | ✅ 可行 | localStorage 存当前 N 级别 |
| 卡片尺寸 | `aspectRatio: "1:1"` | 400×400，网格 + 按钮紧凑但可行 |

**技术判断**：✅ 可行。3×3 位置网格在 400px 宽度内每个格子约 100px，紧凑但足够。单模态（仅位置）可以在卡片中完整实现。

### 3.6 任务切换（多规则切换 + 快速响应）

| 验证项 | 结果 | 证据 |
|--------|------|------|
| 多规则显示 | ✅ 可行 | DOM 文本/颜色提示 |
| 规则随机切换 | ✅ 可行 | JS 随机 + DOM 更新 |
| 快速响应 | ✅ 可行 | 点击事件 + performance.now() |
| 切换成本计算 | ✅ 可行 | JS 逻辑 |
| 卡片空间 | ⚠️ 紧凑 | 规则提示 + 刺激 + 响应区需要同时可见 |
| 卡片尺寸 | 推荐 `aspectRatio: "4:3"` | 400×300 |

**技术判断**：✅ 可行但空间紧凑。任务切换需要规则提示区 + 刺激展示区 + 响应区三者同时可见。在 400×300 空间内需要精简 UI——推荐用颜色边框而非大段文字做规则提示。

## 四、卡片能力边界总结

### 4.1 卡片的硬限制

| 限制 | 具体值 | 影响 |
|------|--------|------|
| 最大显示尺寸 | **400×600px** | 大棋盘/多元素排列受限 |
| sandbox 无 `allow-forms` | 不能 `<form>` 提交 | 需用 fetch POST 替代，实际无影响 |
| sandbox 无 `allow-popups` | 不能 window.open() | 训练游戏不需要弹出窗口，实际无影响 |
| 无 `external.open` | 不能在浏览器打开链接 | 训练游戏不需要，实际无影响 |
| 无 `clipboard.writeText` | 不能写剪贴板 | 训练游戏不需要，实际无影响 |
| 无键盘焦点 | iframe 默认无焦点 | 键盘游戏需额外点击，推荐改用点击交互 |
| 无用户手动调整大小 | 固定 iframe 尺寸 | 需要通过 `hana.resize()` 程序化调整 |
| 5 秒自动 ready | 即使不调 hana.ready() 也会就绪 | **反而是优势**：不需要 `@hana/plugin-sdk` 依赖 |

### 4.2 卡片相对 Widget 的优势

| 优势 | 说明 |
|------|------|
| **不需要 @hana/plugin-sdk** | 5s 自动 ready，纯 HTML 就能跑 |
| **与消息上下文绑定** | 卡片在对话流中，可以直接关联到"Agent 出题"的那条消息 |
| **轻量** | 不需要面的板概念，即用即走 |
| **无障碍降级** | PluginCardBlock 有 text fallback（`card.description`），不支持 iframe 的环境也能看到文字 |

### 4.3 卡片相对 Widget 的劣势

| 劣势 | 说明 |
|------|------|
| **尺寸受限** | 400×600 硬上限，Widget 可利用整个右侧面板 |
| **生命周期短** | 滚出视口可能被销毁，Widget 持续存在 |
| **键盘焦点** | iframe 无默认焦点，Widget 面板打开时宿主可帮助管理焦点 |
| **不适合长会话** | 如果游戏需要跨多条消息持续运行，Widget 更合适 |

## 五、综合结论

### 6 个候选游戏的卡片可行性

| 游戏 | 卡片可行 | 推荐 aspectRatio | 注意事项 |
|------|---------|-----------------|---------|
| 舒尔特表格 | ✅ 完全 | `1:1` (400×400) | 卡片最适合的游戏 |
| Stroop 色词 | ✅ 完全 | `4:3` (400×300) | 无限制 |
| Go/No-Go | ✅ 可行 | `4:3` (400×300) | 推荐点击版，避免键盘焦点问题 |
| 数字广度 | ✅ 完全 | `4:3` (400×300) | 无限制 |
| N-Back（单模态） | ✅ 可行 | `1:1` (400×400) | 3×3 网格在 400px 内紧凑但可行 |
| 任务切换 | ✅ 可行 | `4:3` (400×300) | 空间紧凑，需精简规则提示 UI |

**结论**：全部 6 个游戏都可以以卡片形式实现。没有任何一个需要降级到 Widget。

### 核心判断

**卡片的能力边界不在 sandbox，而在尺寸。** 当前 `allow-scripts allow-same-origin` 足以支撑任何纯前端交互游戏。唯一的硬限制是 400×600px 的显示空间——这对舒尔特表格（400×400）和简单选择游戏完全够用，对复杂的多面板游戏（如 WCST）不够。

### 推荐架构

卡片模式（而非 Widget）更适合认知训练游戏的场景：

1. **自然上下文**：卡片嵌入在对话流中，Agent 出题 → 卡片展示 → 用户互动，流程连贯
2. **零依赖**：不需要 `@hana/plugin-sdk`，纯 HTML/CSS/JS 可直接参考 TTS 播放器模式
3. **渐进复杂度**：
   - 阶段一：纯前端卡片游戏（舒尔特表格），localStorage 存分数，像 TTS 一样 standalone
   - 阶段二：卡片 + plugin tool 联动（Agent 出题 → tool 写题目文件 → 卡片 fetch 获取）
   - 阶段三：多游戏轮换（每日挑战），卡片内切换游戏类型

### TTS 音频条的可复用模式

```js
// 插件 tool 返回（参考 generate_speech.js:55-63）
return {
  content: [{ type: "text", text: "游戏结果文本" }],
  details: {
    card: {
      type: "iframe",
      route: `/game?type=schulte`,  // 游戏路由
      aspectRatio: "1:1",
    },
  },
};

// 路由 handler（参考 player.js 模式）
app.get('/game', (c) => {
  const gameType = c.req.query('type');
  const html = renderGame({ gameType }); // 纯 HTML/CSS/JS
  return new Response(html, { headers: { 'Content-Type': 'text/html; charset=utf-8' } });
});
```

这是已验证的生产级模式。TTS 音频条已经在生产环境中证明了：
- iframe 卡片可以运行完整的交互式 JS
- `sessionStorage` 可以在卡片间保持状态
- `IntersectionObserver` 可以感知可见性
- `<audio>` 可以播放媒体
- 所有操作都在 400×600 的卡片空间内正常工作
